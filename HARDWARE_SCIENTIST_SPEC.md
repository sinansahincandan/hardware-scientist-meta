## 0. Non-negotiable rules (read first)

1. **Working end-to-end beats polish.** Build milestone by milestone (§11). After every milestone: run `pytest -q`, run the fake-mode demo, write `CHECKPOINT.md`. Do not start the next milestone with a failing test.
2. **Do not redesign the architecture.** Implement the loop in §3–§7. If something is impossible or ambiguous, write the question and the default you chose into `QUESTIONS.md` and continue. Do not stop to ask.
3. **Use only the Responses API** (`POST /v1/responses`) for all language/vision calls. Do not use Chat Completions (no reasoning carry-over across turns, no `web_search`, no reasoning summaries). Use the field names in §9. Do not invent parameters; anything not in §9 must be looked up at `https://dev.meta.ai/docs/` before use. Items in §14 are **unverified** and must be confirmed by a smoke test before the design relies on them.
4. **Feedback is written text; structure only where Python must choose a branch.** The judgments in this system (evaluation, design review, the Manager's diagnosis, prompt rewrites) travel between LLMs as **free written text**. There are **no numeric scores and no issue categories**. Structured output (`text.format`, JSON Schema compatible with `strict: true`: root object, `additionalProperties: false` on every object, every key in `required`, no `allOf`/`oneOf`, no recursive `$ref`) is used only to carry the few yes/no decisions and lists that the controller must read — e.g. `accept`, `s1_faithful`, `s2_flaw`, `same_problem_as_before` — next to the free-text fields, and for data that code must draw (`SolutionPrompt` parts, `SchematicSpec`). Never parse free text to make a control-flow decision.
5. **Pixels from the image model, words from code.** `muse-image-1.0` renders images with **no text, labels, numbers, arrows, or logos**. All annotation (labels, leader lines, arrows, scale bars, panel letters, captions) is drawn by Python (Pillow / matplotlib) from schematic data.
6. **No hand-made knowledge inputs.** No rubric files, no seed rules, no hints or expected answers written by hand. The only hand-written inputs are the three fixed demo problems in `examples/01_…`, `02_…`, `03_…` (problem statements only); further problems are generated by `muse-spark-1.3` (§8). The only persistent file across problems is `lessons.md`.
7. **Budget-safe by construction.** Fake mode (`HS_FAKE=1`) runs the whole pipeline with zero API calls and synthetic `usage` numbers. Caps (§7) are enforced in code; the cost cap is checked **before every API call**. Every call's `usage` is logged to `cost.json`.
8. **Secrets:** read `MODEL_API_KEY` from the environment only. Never write it to disk or logs.
9. **Sandbox:** LLM-written calculation/simulation/sketch code runs only in a subprocess (§4.4 sandbox spec). Never `exec()` it in-process.
10. **Language:** code, prompts, docs, and figure labels in English.

## 1. What the system is

Hardware Scientist (HS) is a **conceptual hardware design system**. Input: a problem statement with constraints. Output: an **accepted concept** (structured "solution prompt") and a **concept figure** (panels A–D, §5.6) that lets an engineer grasp in seconds what the device is, which part is critical, how it is measured, and roughly how it is made.

It emulates an experienced PhD engineer who leads a team of domain experts: split the problem into functions, generate concepts per function (including distant cross-domain analogies), argue them out in a meeting, get the proposal judged, and revise **how the team works** when the proposal fails.

**Scope limits.** Conceptual design only. No CAD, no FEA, no detailed drawings. Dimensions are **size classes** (±2–3×). Topology (which parts, how connected) matters more than numbers.

**What is optimized, and how.** No model weights are trained. Two variables are optimized per problem, TextGrad-style (textual feedback → targeted edits):

- the **Master prompt** (Stage A), edited section-wise by the Manager after a failed evaluation;
- the **VLM prompt** (Stage B), rewritten by the VLM prompt writer after a failed S1 check.

Across problems, only `lessons.md` persists (structural lessons about the process, prompts, tools, and image-model quirks — never problem content).

## 3. Inputs and the Master prompt

### 3.1 Problem input
`problem.json` (schema §12.10):
```json
{"title": "...", "statement": "...", "constraints": ["..."], "criteria": ["..."], "attachments": []}
```
`constraints` may be sparse and `criteria` may be empty — a real engineer rarely gets a full spec at concept stage. **Missing constraints are established by the council:** in cycle 1, members look up reasonable values (standards, literature, datasheets, comparable products) with `web_search`, post each as a whiteboard concept tagged `assumed_constraint` with the source as evidence, and the room may challenge them like any other claim. The Secretary copies the surviving ones into `SolutionPrompt.assumed_constraints`; the Evaluator judges the solution against the given constraints **and** checks that the assumed ones are reasonable and sourced. `attachments` may hold image paths (photo of a test machine, a sensor); they are passed to council members as `input_image`.

### 3.2 Master prompt = one Markdown document with fixed headings
The Master prompt is plain Markdown. Code only relies on the **headings**, never on the prose under them:

```
# Master prompt — <problem title> — Rev <N>
## 1. Problem            problem.json verbatim (written by code; never editable)
## 2. Roles              one "### <member name>" sub-heading per member; free text below each (domain, persona, what to challenge)
## 3. Tools              free text: when to use which tool, what new tools exist (all tools are always available, §4.4)
## 4. Meeting protocol   free text: what each cycle is for, how objections are raised/resolved, when to vote
## 5. Criteria           free text; must always contain the two fixed criteria verbatim:
                         "The concept must work physically (no violated conservation law, load path, or signal path)."
                         "The concept must be buildable with purchasable parts and ordinary lab/shop methods."
## 6. Lessons applied    lines copied from lessons.md that apply here
```

Code splits the document on these headings. The roster is the list of `###` names under §2; each member's instructions are its own `###` block plus §1, §3, §4, §5, §6. The number of cycles is a code cap (`config.py`), not part of the prompt.

**Rev 0** is one `muse-spark-1.3` call (free Markdown output): input = `problem.json` + full `lessons.md`; the model writes §2–§6 and chooses 3–5 members with distinct domains for this problem. Code writes §1, inserts the two fixed criteria and the problem's own criteria verbatim if missing, and checks the headings (missing heading → one re-ask).

**How the Master prompt is improved (TextGrad-style, section by section):**
- The optimizer reads the Manager's written diagnosis and the current document and **rewrites any sections it judges necessary, as much as it wants** — one sentence or a whole section. Adding or removing a member = adding or removing a `###` block. Output (structured): `{sections: [{heading, new_text}], change_note}` where `change_note` is a short paragraph "what I changed and why".
- **Code guards (the only hard rules, round 3 B11):** §1 unchanged; both fixed criteria still present verbatim in §5. There is no member-count guard. Guards are checked **per section** (round 3 A3): the sections that pass are applied; only a violating section is sent back once with the reason; if it still violates, that section keeps its old text. An optimizer heading whose number and title name different sections is not applied and is recorded. Every optimizer output, re-asks included, is saved (`rewrite.json`, `rewrite_guard_reask.json`, `rewrite_shrink_reask.json`); reverted sections always produce a saved revision.
- **Shrink check (protection against silently losing content):** if a section loses more than half of its length in one step, the optimizer is asked once: "section X lost N % of its text — intended?" with the removed lines shown. Whatever it answers the second time is applied. **(round 3 A3)** The Manager's agenda (`Gradients.agenda`) is written by code into §4 under "### Agenda for the next meeting (Manager)", replacing the previous agenda.
- Each revision is saved as `master_prompt/rev_{N:03d}.md`, with `diff_{N:03d}.md` (red/green line diff per section + the `change_note`). Nothing is overwritten.
- **Repeated problem → targeted repair.** In its diagnosis the Manager also answers, as written judgment, whether this failure is **the same problem as the previous failure** and, if so, **which earlier change most likely caused or failed to fix it**. It may name sections to revert: `revert_sections: [{heading, to_revision}]`. Code copies those sections' text from that revision; everything else keeps its current text. The optimizer then works on the reverted sections with the Manager's note.
- New tools created by members (§4.4) live in a registry `runs/<id>/tools/<name>.json` independent of revisions; code adds a one-line mention to §3 when a tool is registered. Reverts never unregister a tool.
- **Bound per iteration:** one optimizer call (+ at most one guard re-ask and one shrink re-ask). If nothing changed, record `no_progress` and rerun once; two consecutive `no_progress` iterations → best-effort exit (§7).

## 4. Stage A — Design (instance optimization of the concept)

Per iteration `k`: inspirations → **meeting in one room around a shared whiteboard** (several cycles, closes on consensus or cap) → Secretary → Evaluator → on failure the Manager edits the Master prompt.

Physics lives **inside the discussion**: members compute and simulate with code tools (§4.4), every result is posted to the whiteboard as numbered evidence, and members cite it where it helps. There is no separate physics box; the Evaluator judges against the evidence the room produced.

### 4.1 Inspirations
`CouncilArchive` holds every past solution of this problem with `id`, `status` (`accepted`, `rejected`, `rejected_by_designer`) and the written feedback that rejected or accepted it. A small `muse-spark-1.3` call in the **Manager's** persona (low effort, structured output `Inspirations`, §12.11) picks **1–3 inspirations**, at least one with a rejected status if any exist. They are pinned on the whiteboard (`inspirations` section) before cycle 1. Empty archive → skip.

### 4.2 The room: shared whiteboard + transcript
All members argue in one room and share the same context. Two shared objects, both shown to **every member on every turn**:

- **Whiteboard** (`whiteboard.json`, rendered to `whiteboard.md`; schema `Whiteboard`, §12.15) — the room's single shared state:
  - `inspirations` — pinned archive picks (read-only).
  - `functions` — functional decomposition (`F1`, `F2`, …).
  - `concepts` — candidate concepts per function (`C1`, …; `function_id`, text, author, status `open | favored | dropped`). Distant cross-domain analogies are welcome here.
  - `evidence` — results of `calc`, `simulate`, `sketch`, `web_search` (`E1`, …; author, tool, purpose, code or query, inputs with units, output summary, sketch path, status `ok | error`). **Written by code when a tool runs; members cannot edit or delete evidence.**
  - `objections` — (`O1`, …; author, target id, text, `blocking: bool`, status `open | resolved`, resolution text + evidence ids).
  - `proposal` — the current integrated proposal (version number, author, text, concept ids, `key_claims: [{claim, evidence_ids}]`; evidence ids optional).
  - `votes` — each member's latest vote on the current proposal version (`ready: bool`, reason). Any `update_proposal` increments the version and clears all votes.
- **Transcript** — the spoken part: one free-text message per member turn (≤ 250 words; a longer turn is re-asked once to shorten, never cut by code — round 3 A6).

Members write to the whiteboard **only** through the `whiteboard` function tool (§4.4). Code validates every op (ids exist, author is the caller, a resolution cites at least one evidence id or gives a reason) and returns errors as tool output text.

**Rendering rule (keeps context bounded):** dropped concepts and resolved objections render as one line; evidence renders as one summary line each (`E7 [calc, Mechanics] cantilever tip deflection = 0.42 mm (ok)`); full code/output is fetched with `whiteboard(action="read_evidence", id=...)`. Code warns in `trace.md` if the rendering exceeds ~30k tokens (chars/4).

### 4.3 Turns, cycles, and closing the meeting
- **Turn** = one member speaks. Each turn is a **fresh Responses chain** (tool loop chained with `previous_response_id` inside the turn only). Input: `instructions` (the member's own `###` block from §2 + Master prompt §1, §3, §4, §5, §6) and one user message containing: the rendered whiteboard, the transcript messages since this member's last turn (verbatim), and the member's own previous message. Tool cap **6 calls per turn** (`whiteboard` calls do not count; they have their own cap of 8 per turn); from the 5th counted call `parallel_tool_calls: false`; at the cap pending calls get the output `"tool budget exhausted — write your message now"`; if the model still only calls tools, the last `message` text of the turn is taken and the event logged. Effort: medium.
- **Cycle** = every member takes one turn. Order rotates: cycle `c` starts with member `c mod n`.
- **Protocol** (default text of Master prompt §4 `protocol_text`, editable by the optimizer): cycle 1 — decompose into functions, propose concepts per function, post first estimates; cycles ≥ 2 — attack and defend with evidence, raise/resolve objections, integrate a proposal, vote. **(round 3 A5)** The protocol names who integrates: from cycle 2 the member whose concepts are favored for the most functions writes the proposal; if none exists when cycle 2 ends, the Manager names who writes it in cycle 3.
- **Closing rule (deterministic code, checked once `min_cycles` cycles are complete; a cycle closes only after the Manager's turn, so an objection the Manager raises counts — round 3 A4):** the meeting closes with `closed_by: "consensus"` when all hold:
  1. a `proposal` exists;
  2. every member's latest vote is `ready: true` for the current proposal version;
  3. no open objection has `blocking: true`;
- **Final vote round:** after the last cycle (`MAX_CYCLES`), if a proposal exists and consensus is not reached, code runs one **vote-only round**: every member gets one short request showing the current proposal, open objections and evidence, with only `whiteboard` actions `vote` and `raise_objection` allowed (no `update_proposal`). Consensus in this round closes with `closed_by: "consensus"`.
- **Caps:** `MIN_CYCLES = 2`, `MAX_CYCLES = 4` (code caps in `config.py`; `MIN_CYCLES` is clamped to ≤ `MAX_CYCLES`). No consensus after the vote-only round closes the meeting with `closed_by: "cap"`; open blocking objections are copied by code into `SolutionPrompt.open_questions` and flagged to the Evaluator.
- **Speaking rule (round 3 B8/B9/B10, in the seed §4 text and in every turn instruction):** every member and Manager turn says each point in plain words first, then only the numbers that decide it (units, at most three significant figures); one point per short paragraph, at most three points; ends with the speaker's position. Literature is cited only when it is on the whiteboard as search evidence the speaker has read (by id and title), never from memory — there is no "according to <author, year>" slot. Members address each other only by their roster names (the turn input lists them). Key results are checked against everyday scales and known regimes (accelerations in g, sizes against a person or a door, loads against body weights, energies against daily use). Ids never stand alone ("the 760 mm standard door width (E10)"); abbreviations are defined on first use; other members are addressed by name. Stage A speech is about the device only — never about the figure pipeline. **(round 3 A6)** There is no LLM turn check; code counts words and re-asks a turn over the limit once to shorten it (members and Manager alike); the text is never truncated.
- **Evidence reuse (v2):** a member reads existing evidence before computing and reuses an item by its id unless they state why they recompute it. **Sketching (v2):** a member posts a labeled sketch when proposing or changing a concept whose geometry, mechanism or flow path matters (not a gate, not for purely numerical turns). **Flow view (v2):** the council decides in the meeting whether a flow view is needed and which quantity governs the design (load, heat, energy, fluid, signal); the Secretary records the choice with the solution; the Secretary's transfer line is "<governing quantity>: A → B → C | Measured: D → E".
- **Manager sits in the room as process lead (v2).** The Manager sees the same whiteboard and transcript and takes **one turn at the end of every cycle, after the members**. In its turn it steers the process only: it points out a critical quantity nobody computed, an objection closed without evidence, a vote that came too early, or a missing expertise; it asks a named member to compute, sketch or look something up; it may raise or resolve **process** objections and call `new_tool` (§4.6, cap `MAX_MANAGER_NEW_TOOLS = 2`). It **never proposes design concepts and never votes**; consensus stays with the members. It keeps short written notes per member during the meeting (`manager_notes.md`), which step 2 of §4.6 reads. Its turns appear on the whiteboard replay in its own colour. After the meeting it also reads the full transcript, the whiteboard history and code-computed per-member stats.
- **Secretary** (`muse-spark-1.3`, high effort, structured output `SolutionPrompt`, §12.1): synthesizes from the final whiteboard + transcript. It copies evidence ids into `key_estimates[].evidence_ids` where they exist, and it must not add design ideas that are not on the whiteboard.

### 4.4 Shared tools
| Tool | Type | Implementation |
|---|---|---|
| `whiteboard` | function | `{action, ...}` with `action ∈ add_function, add_concept, set_concept_status, raise_objection, resolve_objection, update_proposal, vote, read_evidence` (schema §12.16). The only write path to the shared board. |
| `calc` | function | `{expression: str, purpose: str}` → evaluated in the sandbox with `math`, `numpy` and **`pint` units** (`Q_(2.1, "GPa")`). Returns value with units or the error. Auto-posted as evidence; the tool output starts with the new evidence id (`"E12: 0.42 millimeter"`). |
| `simulate` | function | `{script: str, purpose: str}` → short numpy/scipy/pint script in the sandbox (ODE, small lumped model, sweep). Stdout ≤ 4 kB. Auto-posted as evidence with the script. Order-of-magnitude modelling only; no FEA. |
| `sketch` | function | `{script: str, caption: str}` → matplotlib script that saves `sketch.png`; auto-posted as evidence (image path); the PNG is shown to the **calling member** in the same request as the tool output (`function_call_output` + a user `message` with `input_image`; fallback two requests, §14.3). Other members see the sketch thumbnail in the next turn's user message (≤ 4 newest sketches attached as `input_image`). |
| `web_search` | built-in | `{"type": "web_search", "search_context_size": "low"}`. **(round 3 B8)** Every member request that offers search sends `include: ["web_search_call.results"]`; every result of every `web_search_call` (title, URL, query, the passage when the API returns one) is posted as one evidence item as soon as the response arrives — including the turn's final response — and, when a turn added search evidence, one extra chained request lists the new ids so the member can cite them. As soon as a response in the turn contains `web_search_call` items, code posts one evidence entry per cited source (`message.annotations[].url_citation`, plus `web_search_call.results` if §14.2 confirms the include works with chaining). If the turn's final response contained new search evidence, code runs **one extra chained request** in the same turn listing the new E-ids and allowing only `whiteboard` calls, so the member can cite them. **Citations (v2):** every search result is resolved at record time to authors/organisation, title, year and URL and stored in the evidence item; an unresolvable token is stored as "unresolved source" with its search query — raw search tokens never appear in speech, and no reference is dropped silently. Each run produces a numbered reference list (`references.md`); the whiteboard and the report link citations to it. |
| `new_tool` | function | `{name, description, parameters (JSON Schema object), python_source, smoke_test_input}` → registered for this problem only after the sandbox smoke test passes; injected into every member's `tools` from the next turn; stored in the tool registry (§3.2). Cap 2 per problem. Its results are auto-posted as evidence too. |

Function tool schemas use the **flat** Responses format and are sent **non-strict** (`strict` omitted); code validates arguments and returns one-line errors (strict structured output applies to `text.format` only). For `calc`, `Evidence.inputs` is filled by parsing the `Q_(...)` literals in the expression. Names match `^[a-zA-Z0-9_.-]+$` with at most one dot; never `browser.search|open|find`.

**Sandbox spec (`sandbox.py`):** run `sys.executable -I launcher.py <script>` (the project's own venv interpreter; **not** `-S`, which would hide numpy/scipy/matplotlib/pint). `launcher.py`: sets `MPLBACKEND=Agg`, `MPLCONFIGDIR=<tmpdir>`, `OPENBLAS_NUM_THREADS=1`, `OMP_NUM_THREADS=1` **before any import**; installs a `sys.meta_path` hook that applies the allow-list (`math, cmath, statistics, random, json, numpy, scipy, matplotlib, PIL, pint`) **only to imports whose calling frame is the user script** (library-internal imports such as `os`, `re`, `ctypes` pass); strips the environment to `PATH`/`HOME` plus the variables above; limits: 10 s wall clock (`subprocess.run(timeout=)`), `RLIMIT_CPU=10`, `RLIMIT_AS=2 GB`, `RLIMIT_FSIZE=20 MB`; cwd = a fresh temp dir; stdout/stderr captured (≤ 4 kB each). Test: `import numpy, matplotlib.pyplot, pint` succeeds; `import socket` from the user script is refused.

### 4.5 Evaluator (judge)
**Inputs:** Master prompt §1 and §5, the `SolutionPrompt`, the evidence table (whiteboard evidence entries, available for lookup), and the meeting closure (`closed_by`, open blocking objections). **Never the transcript.**

Two calls:
1. **Prior-art check** (`muse-spark-1.3`, low effort, `tools=[web_search]`, free text): "find the closest existing product, patent or paper to this concept and state the difference." Output saved as `novelty.md` with its `url_citation`s.
2. **Verdict** (`muse-spark-1.3`, high effort, structured output `Verdict`, §12.2), with the prior-art text as an input.
   - The Evaluator writes its judgment as **free text**, like a senior engineer's review: does it work, can it be built, what is wrong or missing, what would make it better, how it compares to the closest prior art. No scores, no categories.
   - It judges with its own engineering knowledge and does **not** demand evidence for every claim. **(round 3 B8/B10/C18)** It names each key claim that rests on no evidence or source on the board, checks key numbers against everyday scales and known regimes, re-derives the arithmetic that decides acceptance, and lists the measurable deviations with whether each matters for the working principle. When a claim looks implausible, surprising, or is critical and borderline, it looks at the cited evidence; if there is none or it does not hold (wrong model or regime, inconsistent inputs, units), it adds an `evidence_request` — one sentence: the claim, why it is doubtful, what to compute or look up.
   - `accept: bool` is its decision (works and buildable). Novelty is discussed in the text but never decides acceptance. **(round 3 A4)** No code rule overrides it: the Evaluator receives the closure facts (consensus or cap, cycles, whether a proposal formed and who voted ready, every open objection with its author and blocking flag) and judges in writing what they mean.
- Every verdict is appended to `CouncilArchive` with the solution (`source: "evaluator"`).
- **Evidence requests go back to the room:** in the next meeting, code pins each `evidence_request` on the whiteboard as an open **blocking objection authored by "Evaluator"** (and the full feedback text as a pinned note), so the closing rule cannot close the meeting until a member resolves it.

### 4.6 Manager (two-step textual gradient + optimizer) (v2)
TextGrad chain: the output is judged first, then the prompt that produced it. Two separate Manager calls, both saved per iteration (`gradient_output.json`, `gradient_prompt.json`):
1. **Step 1 — output gradient** (`manager_output_gradient`, high effort, structured `OutputGradient`). Input: the `SolutionPrompt` and the written feedback (evaluator verdict, or designer feedback **with its regions**). Output: per feedback item or region, in writing, what in the solution or on the whiteboard must change.
2. **Step 2 — prompt gradient** (`manager_prompt_gradient`, high effort, structured `Gradients`, §12.3). Input: the step-1 output, the transcript, the whiteboard history, per-member stats, the Manager's own meeting notes (§4.3) and the current Master prompt. Output: per section and per member, which part of the prompt or which behaviour produced that output and how it should change; **every diagnosis item cites the step-1 item it explains**. The Manager states in writing whether the problem is **targeted or broad**; the optimizer writes that judgment as this iteration's agenda into Master prompt §4 Meeting protocol (plain prompt text — no new control-flow field). The Manager **diagnoses the process** (wrong expert mix, nobody computed the critical quantity, an objection was closed without evidence, the protocol let the room vote too early, a missing criterion) and member **engineering behaviour** (what the council should know or do differently as engineers: design knowledge, checks to run, comparisons to make). It never proposes a design, and it never writes pipeline rules: retry limits, caps and gating already live in code and stay there.
3. **Revert** (code): only if the Manager named sections to revert.
4. **Optimizer** (medium effort, structured output `MasterPromptRewrite`, §12.4) consumes **step 2 only**. Input: the current document and the step-2 notes. Output: new text for the sections it chooses to rewrite + `change_note`. Guards and shrink check per §3.2; **every** rewrite on **every** path is saved as `rev_N.md` + `diff_N.md` (code in `master.build_next()`); next iteration starts.
5. **Manager tools:** in its diagnosis phase the Manager may call `new_tool` under the same sandbox, smoke test and registry as members (§4.4), cap `MAX_MANAGER_NEW_TOOLS = 2`. All tools stay always available to all members; there is no tool assignment.

If `Verdict.accept` is true, Stage A ends and the accepted `SolutionPrompt` goes to Stage B.

## 5. Stage B — Visualization (instance optimization of the VLM prompt)

Runs on the **accepted** `SolutionPrompt`. See `fig2_visualization_pipeline.png`.

### 5.1 Mechanism sketch (code) (v2)
- One `muse-spark-1.3` call (low effort, structured output `SchematicSpec`, §12.5) converts `SolutionPrompt.concept` into a **2D mechanism sketch**: nodes (parts) with size class and grid layout, edges between parts (`ConnectionKind`), external loads/signals (`loads`), the critical part id, scale-bar length, `view: "top" | "side"`.
- `render_schematic(spec)` is **deterministic Python** (matplotlib, Agg) and must read as a mechanism sketch, not a grid of boxes: **parts at real relative proportions** (size from the geometric mean of each size class, in mm, on a shared scale); **joints and connections drawn as they are** (edge lines meeting part boundaries; hinge circles for revolute connections where the spec marks a joint); **arrows for motion, load and pull directions** (loads as arrows at the part boundary, motion arrows on moving parts); **key dimensions** (overall extent and the critical part's size as dimension lines in the labeled version). Direction, orientation and scale must be encoded, because the S1 source trace (§5.5) can only detect errors the sketch encodes. Two files: `schematic.png` (**no text**, used as the image-model reference) and `schematic_labeled.png` (labels + dimension lines + load letters, used by evaluators and humans). The exact pixel geometry (`px_per_mm`, node boxes) is written to `schematic.json`.
- Code checks: every part in `SolutionPrompt.concept.parts` appears as a node; every edge/load endpoint exists; the graph is connected; sizes within class; `critical_part_id` exists. Failure → re-ask the spec call once with the error list. Second failure → **design incoherent**: build a feedback text from the check errors ("the concept cannot be drawn consistently: <errors>"), mark the archive entry `rejected_by_designer`, count one `returns_to_A`, go to the Manager (§7).

### 5.2 VLM prompt writer (LLM, the Stage B variable)
`muse-spark-1.3`, medium effort, structured output `VLMPrompt` (§12.6). **Input:** `SolutionPrompt`, `schematic.png` and `schematic_labeled.png` (as `input_image`), `figure_spec.preferred_view`, and the `ImageArchive` summary (previous prompts + S1 differences for this problem). Output: `prompt` (materials, finish, view, lighting; "clean technical illustration on white; keep the parts, their connections and relative sizes of the reference; perspective may differ from the reference") and `must_not`, to which code always appends: "No text, no labels, no numbers, no arrows, no logos, no watermarks."

### 5.3 Render (`muse-image-1.0`)
`POST /v1/images/edits` as `application/json` with the schematic as the **reference image**:
```json
{"model": "muse-image-1.0",
 "prompt": "<VLMPrompt.prompt + must_not>",
 "images": [{"image_url": "data:image/png;base64,..."}],
 "n": 1, "size": "<WxH aspect of the schematic, e.g. 1536x1024>",
 "output_format": "png", "response_format": "b64_json",
 "reasoning_strength": "high",
 "tool_enablement": {"enable_web_search": false, "enable_image_search": false, "enable_shell": false}}
```
Unknown top-level JSON fields return 400; `mask`, `input_fidelity`, `partial_images` are unsupported. Retries: `503`/`500` with exponential backoff, honoring `Retry-After` when present (503 sends 60 s), max 3 tries and a 4-minute wall-clock ceiling per image. On `content_policy_violation` ask the writer for one rewrite (does not count as an S1 round); a second violation in the same round counts as an S1 failure with `differences=[{what:"content policy block", image_region:"n/a"}]`. Save `render.png`. $0.01 per image; 150 RPM.

**Fallback backend** (`IMAGE_BACKEND = "responses"`, use only if edits ignore the reference badly): `POST /v1/responses` with `model: "muse-image-1.0"`, `input` = `input_text` prompt + `input_image` schematic, `tools=[{"type":"image_generation","output_format":"png","size":...}]` and **no other tools and no `text.format`** (image models accept only the `image_generation` tool); read the `image_generation_call` item's `result` (base64).

### 5.4 Annotate (code + one localization call)
1. **Localization call** (`muse-spark-1.3`, low effort, structured output `Localization`, §12.7): input = `render.png` (≤ 1280 px) + the list of part ids with one-line descriptions from `schematic.json`, with the grounding instruction in the user message next to the image; output = one box per part on the **normalized 0–1000 grid**, `found: bool`, `confidence`. Code converts to pixels using the exact image size sent and clamps to the image.
2. **Overlay (Pillow):** labels with leader lines anchored at box centers (collision-avoided, outside the part), arrows for `loads` (letter from `loads[].label`, e.g. "F") and for edges with a non-empty label (signal), panel letter. **Scale bar:** `px_per_mm = critical box width in px / geometric mean of critical part's size_class_mm`; draw a bar of `SchematicSpec.scale_bar_mm` labeled as a class ("~10 mm"). If the critical part is `found: false`, skip the bar and add it to the eval input. Fonts and line widths scale with image size.
3. `missing_parts = [p for p in parts if not found]` goes to the designer evaluation.

### 5.5 Designer evaluation (VLM) — region-anchored critique (v2)
`muse-spark-1.3`, high effort, structured output `DesignerEval` (§12.8). Input: `annotated.png`, `schematic_labeled.png`, the `SolutionPrompt` summary, `missing_parts`.
- **Regions:** every finding is a region `{box: [x0, y0, x1, y1] on the 0–1000 grid, part_id, observed, expected}` in free text. Grounding convention verified against the Muse image-understanding docs (0–1000 normalized grid, origin top-left; §14). The designer first describes what it actually sees (pixel-first), then anchors each mismatch to a box.
- **Source trace per region:** if the render differs from the mechanism sketch → **depiction fault (S1)**; if the sketch itself is wrong, or silent on this aspect → **design flaw (S2)**. Each region records which of the two it is (`source`). The flow overlay, when the council asked for one (§5.2), is checked like any other region; a wrong or meaningless flow is a depiction fault.
- **S1 — faithful?** Same parts, same connections, same relative sizes, directions, orientations and scale as the sketch. **Perspective and layout may differ**; S1 is about topology, proportion and encoded direction/scale, not camera angle. A render that looks like a diagram, a cartoon or a CAD wireframe is a depiction fault (visual quality bar, AUTOPILOT §4). Output: `s1_faithful` (yes/no) + regions + written differences.
- **S2 — flaw revealed?** Does seeing the thing expose a real design problem (interference, impossible assembly, load path that cannot work, unreachable part, sensor in the wrong place), or is the sketch wrong/silent (source trace)? Output: `s2_flaw` (yes/no) + regions + written explanation pointing at a **concrete feature of the image**. S2 goes back through the existing Manager → Master prompt path (§4.6); there is no separate research branch — research stays the normal job of members and the Manager.

Routing (`designer_eval.decide()` returns `s1_pass | s1_retry | s2_return`):
- `s1_retry`: `s1_faithful` is no and rounds < `MAX_S1_ROUNDS` → rewrite VLM prompt with the written differences (§5.2), re-render.
- `s2_return`: `s2_flaw` is yes, **or** S1 failed `MAX_S1_ROUNDS` times → the designer's written feedback (or "the render never matched the schematic after 3 rounds: <differences>; the concept is probably under-specified") becomes the feedback for the Manager. `archive.set_status(aid, "rejected_by_designer", feedback=...)` so the inspirations call sees why; back to Stage A.
- `s1_pass`: S1 yes and S2 no → compose the final figure (§5.6). Minor remarks from the S2 text go to `rationale.md` as notes.

Every round writes `prompt + render + annotated + eval` to `ImageArchive` and one line to `trace.md` (S1 reason, prompt change).

### 5.5b VLM prompt gradient, local edit, progress check (v2)
S1 follows the same two-step TextGrad chain as Stage A:
1. The designer regions **are** the output gradient.
2. **VLM prompt gradient** (`vlm_prompt_gradient`, high effort, structured `VLMPromptGradient`): input = render, sketch, the VLM prompt, the regions. Output: a written diagnosis **per region** (which sentence of the VLM prompt caused it, or what the prompt is missing) plus `fix_mode: "local" | "full"` (structured; `full` when the fix spans several parts).
3. **Local edit + composite:** masks are unsupported, so code asks the image model to edit the **full current render** ("change only X; keep everything else identical"), then pastes back only the region box (small margin, feathered edge) onto the previous render. Code asserts pixels outside the box are unchanged. For `fix_mode = "full"`, the writer rewrites the VLM prompt with the gradient and the render is regenerated.
4. **Progress check** (judge, same regions re-checked): keep the change only if the fixed region passes, previously passing regions still pass, and no seam is visible; otherwise revert **both** the render and the VLM prompt and log the revert. All of this counts inside `MAX_S1_ROUNDS`.
5. **After an S2 redesign:** in the next Stage B attempt, the previously flagged regions are re-checked; fixed and nothing regressed → proceed; a regression uses the existing `same_problem` / `revert_sections` mechanism (§3.2, §4.6).

### 5.6 Final figure (panels A–D)
Composed by code into one PNG (`final/figure.png`, 2 columns) + `final/rationale.md`. Image budget for this step: `MAX_FIGURE_IMAGES = 8`.
- **A — System view:** the annotated render that passed.
- **B — Critical part:** zoomed crop of A around the critical part's box (upscale ≤ 2×) with the scale bar. If the crop is < 300 px on its short side, request one close-up render whose **reference is a crop of `schematic.png` around the critical node and its direct neighbours** (re-rendered by `render_schematic` on that node subset), writer prompt "close-up of <critical part> and its neighbours"; run `LightCheck` (§12.13) once, one retry; if it still fails, use the crop of A.
- **C — Measurement chain:** code-only block diagram from `SolutionPrompt.measurement_chain` (sensor → conditioning → instrument → computer). No image model.
- **D — Fabrication:** one render per `fabrication_steps[i]` (3–5). **Reference = a per-step schematic subset** rendered from `fabrication_steps[i].parts_present` after code repair (drop unknown ids; make the sets cumulative across steps; an empty step 1 defaults to the largest part; the last step must contain all parts — log every repair in `trace.md`); writer prompt per step; code captions "1. deposit …". One `LightCheck` per panel ("does it show step i with exactly these parts?"), **no retry**; a failed panel is kept, marked with a small hollow marker in the caption, and listed in `rationale.md`.
- `rationale.md`: solution summary, key estimates with method, risks, novelty claim, sources (`url_citation`s collected from member turns), the Master prompt revision history (ops + reasons), and S1/S2 history.

## 6. Lessons (cross-problem memory)

`lessons.md` sections: `## Process`, `## Prompts`, `## Tools`, `## Image model`, `## User feedback`.

At the end of each problem, one `muse-spark-1.3` call (medium effort, structured output `Lessons`, §12.9) reads `trace.md` **and** the `ImageArchive` summary (prompts, S1 differences, what finally worked) and proposes ≤ 5 candidates. Code keeps only those that pass all three: (a) `structural: true` (about how the team/pipeline works, not about this device), (b) not a near-duplicate of an existing line (`difflib` ratio < 0.8), (c) ≤ 200 characters. Appended with `[YYYY-MM-DD, run <id>]`.

`hs feedback "<text>"` appends the user's note verbatim under `## User feedback` (exempt from the structural filter; the user is the boss). Rev 0 of the next problem reads the whole file.

## 7. Controller loop and hard caps

```python
def run(problem):
    lessons = Lessons.load(); state = MasterPrompt.rev0(problem, lessons)           # 1 call
    archive = CouncilArchive(run_dir); img_archive = ImageArchive(run_dir)
    returns_to_A = 0; best_pass = None; last = None                                # for the best-effort exit
    for k in range(MAX_A_ITERS):                                                    # default 8
        insp       = Manager.inspirations(archive)                                  # 0–1 call
        room       = Meeting(state, insp).run()                                     # whiteboard + transcript; cycles ≤ MAX_CYCLES,
                                                                                    # closes on consensus (code rule) or cap
        solution   = Secretary.synthesize(room)                                     # 1 call, cites evidence ids
        verdict    = Evaluator.judge(state, solution, room.evidence_table(solution), room.closure)  # prior-art + verdict, no transcript
        aid        = archive.add(solution, verdict, revision=state.rev)
        if not verdict.accept:
            state = Manager.edit(room, solution, verdict)                           # written diagnosis -> (revert on repeat) -> section rewrite (§3.2, §4.6)
            if Manager.no_progress_streak >= 2: break                               # two iterations without an applied op
            continue

        spec, errors = Schematic.spec_and_check(solution)                           # 1–2 calls + code
        if errors:
            fb = feedback_from_schematic_errors(errors); archive.set_status(aid, "rejected_by_designer", feedback=fb)
            if returns_to_A >= MAX_B_RETURNS: break
            returns_to_A += 1; state = Manager.edit(room, solution, fb)
            if Manager.no_progress_streak >= 2: break
            continue
        png = Schematic.render(spec)

        for r in range(MAX_S1_ROUNDS):                                              # default 3
            vlm    = Writer.write(solution, spec, png, img_archive)                 # 1 call
            render = ImageModel.edit(vlm, reference=png)                            # 1 image
            annot  = Annotator.run(render, spec)                                    # 1 call + code
            ev     = DesignerEval.run(annot, spec, solution)                        # 1 call
            img_archive.add(vlm, render, annot, ev); last = (solution, spec, annot, render)
            if ev.s1.faithful: best_pass = last
            decision = DesignerEval.decide(ev, round=r)                            # s1_pass | s1_retry | s2_return
            if decision != "s1_retry": break
        if decision == "s1_retry": decision = "s2_return"                           # S1 failed MAX_S1_ROUNDS times

        if decision == "s1_pass":
            figure = Figure.compose(*last)                                          # ≤ MAX_FIGURE_IMAGES images + light checks
            Lessons.update(trace, img_archive); return Result(figure, warnings=[])
        fb = ev.feedback_text(); archive.set_status(aid, "rejected_by_designer", feedback=fb)
        if returns_to_A >= MAX_B_RETURNS: break
        returns_to_A += 1; state = Manager.edit(room, solution, fb)
        if Manager.no_progress_streak >= 2: break

    # exhausted (iterations, B-returns, two no_progress iterations) or cost cap hit (BudgetExceeded raised by client.py, caught here)
    src = best_pass or last
    figure = Figure.compose(*src, best_effort=True) if src else None
    Lessons.update(trace, img_archive)
    return Result(figure, warnings=["best effort: <reason>"], best_archive_entry=archive.best())
# every exit path ends with: Report.write(run_dir)  -> runs/<id>/report.html (§8)
```

**Caps (`config.py`, overridable by CLI flags):** `MAX_A_ITERS=8`, `MAX_S1_ROUNDS=3`, `MAX_B_RETURNS=2`, `MIN_CYCLES=2`, `MAX_CYCLES=4`, `MAX_MEMBERS=5`, `MAX_TOOL_CALLS_PER_TURN=6`, `MAX_TURN_MESSAGE_WORDS=250`, `MAX_NEW_TOOLS=2`, `MAX_FIGURE_IMAGES=8`, `MAX_COST_USD_PER_RUN=15.00`. `BudgetExceeded` is raised by `client.py` **before** any call that would exceed the cap; the controller catches it and exits through the best-effort path. **(round 3)** A project-wide ledger `budget/ledger.jsonl` records every real call (run id, role, model, tokens, images, SAM calls, searches, USD) and caps total spend across runs at `MAX_TOTAL_SPEND_USD` ($55 for round 3); the same pre-call check uses a worst-case estimate of the call; HTTP 402 billing errors raise `BudgetExceeded` and are never retried.

## 9. Meta Model API cheat sheet (checked against dev.meta.ai docs, Oct 30 2026)

**Client**
```python
from openai import OpenAI
client = OpenAI(base_url="https://api.meta.ai/v1", api_key=os.environ["MODEL_API_KEY"])
```

**Text / vision call (Responses API)**
```python
resp = client.responses.create(
    model="muse-spark-1.3",
    instructions=SYSTEM_TEXT,                 # per-request only; NOT carried by previous_response_id -> resend every call
    input=[{"type": "message", "role": "user", "content": [
        {"type": "input_text", "text": "..."},
        {"type": "input_image", "image_url": "data:image/png;base64,..."}   # images only in user-role messages
    ]}],
    tools=[{"type": "web_search", "search_context_size": "low"},
           {"type": "function", "name": "calc", "description": "...", "parameters": {...}}],
    reasoning={"effort": "high"},             # minimal | low | medium | high | xhigh | max ; "none" -> HTTP 400
    text={"format": {"type": "json_schema", "name": "Verdict", "schema": VERDICT_SCHEMA, "strict": True}},
    max_output_tokens=16000,                  # reasoning tokens count toward this (per-role values in config.py)
    previous_response_id=prev_id,             # chains turns; the server keeps the reasoning context
)
```
- `text.format` is documented as the Responses structured-output parameter with `text.format.strict`; the exact nesting above is the **OpenAI-SDK shape and is unverified on Meta** — confirm in M0 (§14.1) and log the full 400 body if it fails.
- Output items: `reasoning`, `message` (`output_text` blocks with `annotations[].url_citation {url, title, start_index, end_index}`), `function_call` (`name`, `arguments`, `call_id`), `web_search_call`. Select items by `type`, not position.
- Tool results: next request with `previous_response_id` and `input=[{"type":"function_call_output","call_id":..., "output": "<string>"}]`, one per call (the server does not enforce ordering; keep call order anyway). `tool_choice` supports only `"auto"`. `parallel_tool_calls: false` limits to one call per turn.
- Truncation: Meta's documented `status` values are `completed`, `failed`, `cancelled`, `in_progress`, `queued`; `incomplete_details` is named but not described (§14.8). Detect truncation defensively — `status != "completed"`, or `usage.output_tokens >= max_output_tokens - 64`, or the JSON fails to parse — and retry once with double `max_output_tokens` (cap 32k).
- Images: ≤ 50 per request, ≤ 50 MB inline; PNG/JPEG/WebP/GIF. ~1280 px ≈ 1.3–1.5k input tokens; downscale to ≤ 1280 px before sending. Localization answers are on a normalized 0–1000 grid relative to the exact image sent.
- Do **not** send `response_format`, `stop`, `frequency_penalty`, `presence_penalty`, `truncation: "auto"`, unknown `include` values, or `include: ["reasoning.encrypted_content"]` with `previous_response_id`. Leave `temperature`/`top_p` unset.
- Strict schema rules: root is a plain object (no top-level `anyOf/oneOf/allOf/enum/not`); `allOf`/`oneOf` nowhere; `anyOf` allowed below root; every object has `additionalProperties: false` and all keys in `required`; no recursive `$ref`; depth ≤ 10; ≤ 5,000 properties. Build from pydantic and post-process; unit-test the post-processor.
- Errors: `503`/`500` retry with backoff honoring `Retry-After` (max 3); `429` back off per `Retry-After`; `400` log the body and raise (schema or parameter bug); `402` = billing.

**Image model (`muse-image-1.0`)** — §5.3. Use `requests` with `application/json` for `/v1/images/edits` (the `images` array form). JSON body fields: `model, prompt, images[{image_url|file_id}], n (1–10), size (aspect only), output_format (webp|png|jpeg), response_format (b64_json|url), reasoning_strength (low|high), tool_enablement{enable_image_search, enable_web_search, enable_shell}`. Response: `data[0].b64_json`.

**Prices and limits:** `muse-spark-1.3` input $1.25 / cached input $0.15 / output $4.25 per 1M tokens; 3,000 RPM, 4,000,000 TPM per team. `web_search`: $2.50 per 1,000 queries on top of tokens. `muse-image-1.0`: $0.01 per generated image, 150 RPM. `muse-wonder-1.0` ($4 / $20) is not used at runtime. Hackathon credits: $150 per participant per the event announcement — confirm in the dashboard.

**Cost model (write the measured numbers into README):** each member request on a `previous_response_id` chain re-bills the whole context (partly at the cached rate). Each turn is a fresh chain, so context per request is bounded by the whiteboard rendering + recent transcript (~8–15k tokens). Order of magnitude with defaults (4 members × up to 4 cycles = ≤ 16 turns × ~3 requests, ~12k input / ~2.5k output per request, medium effort): member turns ≈ $1.0–2.0 per Stage A iteration; Secretary + prior-art check + Evaluator + Manager ≈ $0.35; searches ≈ $0.05. **Stage A iteration ≈ $1.4–2.4; Stage B round ≈ $0.05–0.10; a problem with 3 A-iterations and 2 B-rounds plus panels ≈ $5–8. The three shipped examples ≈ $15–25 in total.** `cost.json` columns: role, model, input, cached_input, output, reasoning, searches, images, usd.

**Prompting defaults for Muse Spark** (from `https://dev.meta.ai/docs/muse-spark-open/prompting`, written for the open model; apply as defaults): most important rules first; role → objective → priority rules → decision procedure → exact output format → completion condition; do **not** describe tools in the instructions; for vision calls keep the system text short and put grounding instructions in the user message next to the image (`image-understanding`).

**Reasoning effort / `max_output_tokens` per role (`config.py`):** members (per turn) medium/8k; secretary high/16k; prior-art check low/4k; evaluator high/12k; manager-inspirations low/2k; manager-gradients high/12k; optimizer medium/8k; schematic spec medium/8k; VLM writer medium/4k; localization low/4k; designer eval high/8k; light check low/2k; lessons medium/4k; example generator medium/8k.

## 12. Structured-output schemas (pydantic; field names are binding)

Shared enums: `ConnectionKind = "mechanical"|"electrical"|"optical"|"fluid"|"wireless"|"thermal"`; `LoadDirection = "up"|"down"|"left"|"right"|"in"|"out"` (`in`/`out` are drawn by code as ⊙ / ⊗ glyphs). Only drawing data uses enums; judgments are free text.

**12.1 `SolutionPrompt`**
`title`, `problem_restatement`, `assumed_constraints: list[{constraint, source, evidence_ids: list[str]}]`, `functional_decomposition: list[str]`, `concept: {working_principle: str, parts: list[{id, name, function, material, size_class_mm: {min: float, max: float}, qty: int}], connections: list[{from_id, to_id, kind: ConnectionKind, label: str}], loads: list[{on_id, label, direction: LoadDirection}], key_estimates: list[{quantity, value: float, unit, method, evidence_ids: list[str]}]}`, `measurement_chain: list[{stage: "sensor"|"conditioning"|"instrument"|"computer", name, interface}]`, `fabrication_steps: list[{step: int, description, method, parts_present: list[str]}]` (3–5), `risks: list[{risk, mitigation}]`, `novelty_claim: str`, `cost_class: "<$100"|"$100-1k"|"$1k-10k"|">$10k"`, `figure_spec: {system_view: str, critical_part_id: str, preferred_view: "isometric"|"top"|"side"|"section"}`, `open_questions: list[str]`.

**12.2 `Verdict`** — `feedback: str` (free-text review), `evidence_requests: list[str]` (one sentence each; may be empty), `accept: bool`. (`source` = evaluator / designer / schematic_check is set by code, not by the model.)

**12.3 `Gradients`** (the Manager's diagnosis; free text in a light frame) — `per_member: list[{member, what_went_wrong, what_should_change}]`, `per_section: list[{heading, diagnosis, direction}]`, `sections_to_change: list[str]` (headings), `root_cause: str`, `same_problem_as_before: bool`, `repeat_explanation: str`, `revert_sections: list[{heading, to_revision: int}]` (may be empty).

**12.4 `MasterPromptRewrite`** — `sections: list[{heading: str, new_text: str}]` (only the sections it rewrites; any length), `change_note: str`.

**12.5 `SchematicSpec`**
`view: "top"|"side"`, `nodes: list[{id, label, shape: "rect"|"circle"|"beam"|"plate"|"cylinder", size_class_mm: {min, max}, layout: {col: int, row: int}, color_hint}]`, `edges: list[{from_id, to_id, kind: ConnectionKind, label, arrow: bool}]`, `loads: list[{on_id, label, direction: LoadDirection}]`, `critical_part_id`, `scale_bar_mm: float`, `notes: list[str]`. (`scale_bar_mm` here is the only one used for drawing.)

**12.6 `VLMPrompt`** — `prompt: str`, `must_not: list[str]`, `changes_from_previous: str`.

**12.7 `Localization`** — `parts: list[{id, found: bool, box_1000: {x0, y0, x1, y1}, confidence: float}]`.

**12.8 `DesignerEval`** — `s1_faithful: bool`, `s1_differences: str`, `s2_flaw: bool`, `s2_feedback: str` (must point at concrete image features), `notes: str`, plus (v2) `pixel_description: str`, `label_findings: str`, `regions: list[EvalRegion]`, `requirements: list[RequirementCheck]`. **`EvalRegion`** — `box: list[float]` ([x0, y0, x1, y1] on the 0–1000 grid), `part_id: str`, `observed: str`, `expected: str`, `source: "render" | "schematic"` (render ≠ sketch → S1; sketch wrong/silent → S2), `fixed: bool` (set by the progress check). **`OutputGradient`** — `items: list[{feedback_item, must_change}]`, `summary: str`. **`VLMPromptGradient`** — `per_region: list[{part_id, diagnosis, prompt_fix}]`, `fix_mode: "local" | "full"`, `summary: str`. `Gradients` (12.3) gains `agenda: str` (targeted-or-broad judgment, written into Master prompt §4) and each `per_member`/`per_section` item gains `explains: str` (the step-1 item it cites).

**12.9 `Lessons`** — `candidates: list[{text, category: "process"|"prompts"|"tools"|"image_model", structural: bool, evidence}]`.

**12.10 `Problem`** — `title, statement, constraints: list[str], criteria: list[str], attachments: list[str]`.

**12.11 `Inspirations`** — `picks: list[{archive_id: str, why_useful: str}]` (1–3; ≥ 1 non-accepted status when available).

**12.12 Master prompt** — not a schema: a Markdown document with the fixed headings of §3.2 (Rev 0 is free Markdown output, validated by a heading check).

**12.13 `LightCheck`** — `ok: bool`, `reason: str`.

**12.14 `ProblemSet`** — `problems: list[Problem]`.

**12.15 `Whiteboard`** (internal state, not a model output) — `inspirations: list[{archive_id, status, feedback_summary}]`, `functions: list[{id, text, author}]`, `concepts: list[{id, function_id, text, author, status: "open"|"favored"|"dropped"}]`, `evidence: list[{id, author, tool, purpose, code_or_query, inputs: dict, output_summary, output_full, sketch_path, status: "ok"|"error", cycle}]`, `objections: list[{id, author, target_id, text, blocking: bool, status: "open"|"resolved", resolution, evidence_ids: list[str]}]`, `proposal: {version: int, author, text, concept_ids: list[str], key_claims: list[{claim, evidence_ids: list[str]}]} | null`, `votes: dict[member, {version: int, ready: bool, reason}]`, `closure: {closed_by: "consensus"|"cap", cycles_used: int, open_blocking: list[str]}`.

**12.16 `whiteboard` tool arguments** (function-tool `parameters`, validated in code) — `action: "add_function"|"add_concept"|"set_concept_status"|"raise_objection"|"resolve_objection"|"update_proposal"|"vote"|"read_evidence"`, plus optional `id, function_id, text, status, target_id, blocking, resolution, evidence_ids, concept_ids, key_claims, ready, reason`. Code checks which fields each action needs and returns a one-line error otherwise.

## 13. Known limitations to state in README (do not try to solve them now)

- The evaluator is an LLM judge using its own engineering knowledge; it consults code-computed evidence only when a claim looks doubtful. It is not a physical test.
- Novelty is discussed in the Evaluator's text against one web-searched closest prior art; it is not a patent search.
- Prompt-level learning is weaker than weight-level learning; `lessons.md` is a small, filtered memory.
- `muse-image-1.0` reference fidelity is not controllable (`input_fidelity` unsupported); S1 exists because of this; the `responses` backend is a switch, not a fix.
- Dimensions are size classes; no tolerance or detailed geometry.
- One accepted concept per run; alternatives live in `archive.jsonl`, not in the figure.
